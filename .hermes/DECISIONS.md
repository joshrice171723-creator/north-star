# Durable Product and Architecture Decisions

Record decisions that future sessions should not casually reopen. If a decision is superseded, mark it superseded instead of deleting its history.

## D001 — Product identity

**Status:** Active
**Decision:** The product is an AI Executive Coach Command Center, not a certification app.
**Reason:** The user needs one operating system for multiple projects, priorities, execution, review, and AI operations. Learning is one capability within that system.
**Consequence:** Primary branding and navigation must be executive/workflow oriented while preserving the learning module.

## D002 — Learning remains protected

**Status:** Active
**Decision:** Existing curriculum, notes, captures, practice, flashcards, review behavior, persistence, Academy behavior, and working IPC contracts are compatibility boundaries.
**Reason:** Product repositioning must not destroy valuable work or data.
**Consequence:** New command-center features are additive and must not silently migrate or rename learning data.

## D003 — Local-first default

**Status:** Active
**Decision:** Keep the application local-first unless a future phase explicitly approves a backend, sync, or external integration.
**Reason:** Privacy, reliability, and reduced architectural risk.
**Consequence:** New data should use versioned local persistence with clear ownership and rollback behavior.

## D004 — No credentials in the app

**Status:** Active
**Decision:** Do not request, store, expose, or add credentials, cookies, passwords, authorization headers, or secrets.
**Reason:** This is a non-negotiable privacy and security boundary.
**Consequence:** Any provider integration requiring credentials must stop for an explicit architecture/security decision.

## D005 — Coach permissions

**Status:** Active design constraint
**Decision:** The coach may eventually read structured app state and draft recommendations, but data mutations require user approval, are explainable, and must be reversible.
**Reason:** Executive support should increase agency, not create hidden automation.
**Consequence:** Do not build unrestricted autonomous write access.

## D006 — Usage data must be real and attributable

**Status:** Active
**Decision:** The first usage ledger should track requests generated by this app when real provider response metadata is available.
**Reason:** Provider-wide usage cannot be claimed without a verified source.
**Consequence:** Every usage view must identify its source, scope, and limitations; no fake values.

## D007 — ADHD-aware, not clinical

**Status:** Active
**Decision:** Use practical executive-function support patterns such as concrete next actions, reduced overload, focus limits, and visible blockers, without diagnosis or medical claims.
**Reason:** The product should be helpful and safe.
**Consequence:** UX copy and coach prompts must avoid clinical promises.

## D008 — One bounded phase at a time

**Status:** Active
**Decision:** Every session works on one bounded objective; every phase has explicit non-goals, acceptance criteria, verification, and a stop condition.
**Reason:** The product vision is intentionally broad and otherwise will produce disconnected half-built systems.
**Consequence:** Future sessions must not begin later-phase work without explicit approval.

## D009 — Documentation authority

**Status:** Active
**Decision:** Resolve conflicts using: current user instruction, `PROJECT_BRIEF.md`, this file, active phase plan, `PRODUCT_VISION.md`, `PROJECT_STATUS.md`, then older transcripts.
**Reason:** Current scope must override stale historical plans.
**Consequence:** Update the authoritative document when requirements change.

## D010 — Phase 1 shell boundary

**Status:** Active
**Decision:** Phase 1 establishes only the Executive Coach Command Center product shell and information architecture around the existing Learning & Development module.
**Reason:** The broader product direction needs a truthful identity and navigation foundation before new workflow systems are introduced.
**Consequence:** The shell may show existing learning-derived state and clearly labeled planned areas, but must not fabricate projects, tasks, coaching, metrics, integrations, or provider data. Phase 1 stops after build/runtime gates and user acceptance.
